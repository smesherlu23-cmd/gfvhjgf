## 🔴 Критические проблемы

### 1. Нет аутентификации, все пароли отдаются в открытом виде
В `pom.xml` нет `spring-boot-starter-security`, в коде нет сущности пользователя, все эндпоинты открыты. При этом `LoginService.toResponse()` (`service/LoginService.java:91-99`) **расшифровывает пароль и кладёт его в ответ**:

```
GET /entries  →  [{"id":1,"title":"…","username":"…","password":"<открытый пароль>", …}, …]
```

Это значит:
- любой, у кого есть сетевой доступ к `:8080`, получает **все пароли всех записей** одним запросом;
- сейчас, без аутентификации, их можно и **изменить или удалить** (`PUT`/`DELETE /entries/{id}`);
- записи ни к кому не привязаны (в `PasswordEntry` нет `owner`/`userId`), поэтому даже после добавления логина будет утечка между пользователями (IDOR), пока не появится проверка владельца.

### 2. Пароль от БД закоммичен в публичный репозиторий
`pass_manager/src/main/resources/application.properties`:
```properties
spring.datasource.username=postgres
spring.datasource.password=717***   # полное значение есть в репозитории
```
Добавлен в коммите `cb2a635` (05.11.2026), лежит в HEAD до сих пор. Репозиторий публичный. Что сделать:
1. **Сменить пароль** пользователя `postgres` (удаления из репозитория недостаточно: значение останется в истории).
2. Читать его из окружения: `spring.datasource.password=${DB_PASSWORD}`.
3. Завести отдельного пользователя БД с минимальными правами, а не суперпользователя `postgres`.
4. По желанию вычистить историю (`git filter-repo`) и включить GitHub Secret Scanning.

### 3. Архитектура шифрования не «менеджерская»
Шифрование серверное, ключ `PASSWORD_ENCRYPTION_KEY` **один на все записи всех пользователей**. Сервер получает пароль открытым текстом, шифрует его и сам же расшифровывает. Следствия:
- ключ из окружения плюс дамп БД дают все пароли сразу;
- админ сервера или любой, кто прочитал логи или память процесса, видит пароли.

Промышленные менеджеры паролей (Bitwarden, 1Password, KeePassXC) используют **zero-knowledge**: ключ выводится из мастер-пароля **на клиенте** (Argon2id или PBKDF2), шифрует и расшифровывает клиент, а сервер хранит только шифротекст. Для учебного проекта менять схему не обязательно. Но это главное архитектурное решение, и принять его лучше до того, как появятся пользователи и данные.

### 4. Модель данных не соответствует ТЗ
Сверка с документом «Менеджер паролей» (модалка «Add logins»):

| Поле по ТЗ | В `PasswordEntry` | |
|---|---|---|
| Username | `username` | ✅ |
| Alterusername | — | ❌ |
| Password | `encryptedPassword` | ✅ |
| Note | `notes` | ✅ |
| Item name | `title` | ✅ |
| Add a collection | — | ❌ сущности «коллекция» нет |
| Блок доп. информации | — | ❌ |
| *(в ТЗ нет)* | `website`, **обязательное** (`@NotBlank`) | ⚠️ |

Поля `website` в модалке по ТЗ нет, а на бэке оно обязательное. Значит, форма, сделанная строго по ТЗ, **всегда будет получать 400**. Кроме того, в бэкенде нет ничего для:
- пользователя (аватар, ник, почта, регистрация и вход, а `auth.html` во фронте уже есть);
- коллекций (фронт уже ждёт `/api/collections`);
- поиска (`Search`);
- импорта (`Import logins`);
- настроек уведомлений и пользовательских тем (ТЗ требует сохранять кастомную тему).

## 🟠 Существенные проблемы

### REST API и обработка ошибок
- **`PUT /entries/{id}` затирает поля и падает.** `updateEntry` (`LoginService.java:72-82`) присваивает все поля из запроса без проверки на `null`, а `@Valid` у PUT нет. Запрос `{"title":"new"}` занулит остальные поля. Для `encryptedPassword = null` вызов `password.getBytes(...)` в `EncryptionService.encrypt` бросит NPE, она обернётся в `IllegalStateException`, и клиент получит **500**. Нужно либо валидировать PUT как полную замену, либо сделать `PATCH` с частичным обновлением.
- **Ограничения длины только в БД.** Hibernate создаёт строковые колонки как `varchar(255)`, а `@Size` на DTO нет. Заметка длиннее 255 символов даёт `DataIntegrityViolationException`, то есть **500**. С паролем хуже: в базе хранится `Base64(nonce 12 + пароль + tag 16)`, поэтому пароль длиннее **161 байта UTF-8** не поместится. Это 161 латинский символ, но всего 80 кириллических. Нужны `@Size` на DTO и `@Column(length = …)` или `TEXT` для шифротекста и заметок.
- **Одна битая запись ломает весь список.** `getAllEntries()` расшифровывает каждую запись. Если хотя бы одна не расшифруется (сменили ключ, повредили данные), `GET /entries` целиком отдаст 500. Пагинации тоже нет (`findAll()`).
- **Секреты в списке.** Даже с аутентификацией список не должен содержать пароли. Их лучше отдавать отдельным запросом (`GET /entries/{id}/secret`), который проще аудировать.
- **Коды ответов:** `POST` возвращает 200 вместо **201** с `Location`, `DELETE` возвращает 200 с пустым телом вместо **204**.
- **`GlobalExceptionHandler`** ловит только `MethodArgumentNotValidException`. На `IllegalStateException`, `DataIntegrityViolationException` и некорректный JSON отвечает стандартная страница ошибки Spring, и формат ответов получается разным. Стоит перейти на `ProblemDetail` (RFC 9457), он встроен в Spring 6.
- **Тестовые эндпоинты в рабочем коде:**
  - `GET /test-entry` возвращает **JPA-сущность** напрямую, с полем `encryptedPassword: "biwerg"`;
  - `POST /logins` просто возвращает тело запроса обратно (`LoginService.createLogin` ничего не делает);
  - `GET /hello` и `GET /status` с захардкоженной версией `"1.0"`, хотя в pom `0.0.1-SNAPSHOT`. Для этого есть Spring Boot Actuator (`/actuator/health`, `/actuator/info`).
- **CORS не настроен.** Фронт на `:5500` (Live Server) не сможет обращаться к `:8080`.
- Нет общего префикса `/api`, а фронт рассчитывает на `/api/collections`.

### Криптография (детали)
Что сделано **правильно**: AES/GCM/NoPadding, ключ 256 бит с проверкой длины, nonce 96 бит из `SecureRandom` для каждой записи, тег 128 бит, формат `nonce‖ciphertext` в Base64, ключ берётся из окружения, а не из кода. Это хорошая реализация, многие ошибаются именно здесь.

Что улучшить:
- **Нет AAD.** Шифротекст не привязан к записи: если поменять местами значения `encrypted_password` у двух строк в БД, GCM этого не заметит. Нужно передавать `cipher.updateAAD(entryId или userId)`.
- **Нет версии ключа.** Ротация невозможна без массовой перешифровки. Стоит добавить префикс `v1:` или колонку `key_version`.
- Ключ декодируется и проверяется при **каждом** вызове, а не при старте. Если `PASSWORD_ENCRYPTION_KEY` неверной длины, приложение запустится и упадёт на первом же запросе. Лучше проверять ключ в `@PostConstruct` или через `@ConfigurationProperties` с `@Validated`. `SecureRandom` можно создать один раз в поле.
- `throws Exception` в публичных методах. Лучше своё непроверяемое `CryptoException`.
- Нигде не задокументировано, что без переменной окружения `PASSWORD_ENCRYPTION_KEY` приложение не стартует (`Could not resolve placeholder`). В `main` нет README.

### База данных и конфигурация
- `spring.jpa.hibernate.ddl-auto=update`, миграций нет. Схема меняется неконтролируемо, а Hibernate не удаляет и не переименовывает колонки. Нужен **Flyway** или Liquibase и `ddl-auto=validate`.
- `show-sql=true` и `format_sql=true` включены во всех окружениях. Это стоит вынести в профиль `dev`.
- Не задан `spring.jpa.open-in-view=false`, из-за этого Spring Boot пишет предупреждение при старте.
- Нет полей аудита (`createdAt`, `updatedAt`): по ТЗ они не требуются, но пригодятся, например, для сортировки и уведомлений.

### Сборка, тесты, инфраструктура
- **Исполняемый jar не собирается.** В `pom.xml` нет секции `<build>` с `spring-boot-maven-plugin`. `mvn package` соберёт обычный jar без зависимостей и `Main-Class`, и `java -jar` не запустится.
- **Тестов нет совсем.** Нет ни `src/test`, ни `spring-boot-starter-test`. Для `EncryptionService` очевидны юнит-тесты: round-trip, неверный ключ, подмена шифротекста. Для API напрашиваются `@WebMvcTest` и `@DataJpaTest` с Testcontainers.
- Нет Maven Wrapper (`mvnw`), хотя `.gitignore` его упоминает.
- Нет `docker-compose.yml` для PostgreSQL. Нет CI. Нет документации API (springdoc-openapi).
- **Spring Boot 3.5.7 отстаёт на 9 патчей** от текущей 3.5.16, а уже вышла 4.1.2. Минимум — обновиться до 3.5.16 (исправления безопасности).

### Качество кода
- **Имена:**
  - `LoginService` на деле занимается CRUD для `PasswordEntry`, лучше `PasswordEntryService`;
  - в `CreatePasswordEntryRequest` и `UpdatePasswordEntryRequest` поле `encryptedPassword` содержит **открытый** пароль, это вводит в заблуждение;
  - `HelloController` смешивает health-check, тестовые и бизнес-эндпоинты.
- В `HelloController` поле и конструктор объявлены после методов. Импорты `CreatePasswordEntryRequest` и `jakarta.validation.Valid` не используются.
- DTO на Java 21 удобнее сделать `record`: минус ~150 строк геттеров и сеттеров.
- Форматирование: `return toResponse(...);    }` (`LoginService.java:57, 82`). Импорты не упорядочены.
- Опечатки: «Названиек вебсайта обязательно!» (`CreatePasswordEntryRequest.java:9`), в коммитах «decprypt» и «frst commit».

### Репозиторий
- В корне лежат `.DS_Store`, `.idea/` (дважды: в корне и в модуле) и бинарный `Менеджер паролей.pages` с ТЗ. ТЗ лучше хранить как `docs/spec.md`: его видно на GitHub и удобно сравнивать между версиями.
- Корневого `.gitignore` нет, есть только у модуля.
- Ветки `main` (бэкенд) и `frontend` (фронтенд) не имеют общей структуры. Об этом подробнее в [аудите фронтенда](../frontend-audit/README.md).

## 🟢 Что сделано хорошо
- Чёткие слои: контроллер, сервис, репозиторий. Зависимости внедряются через конструктор, а не `@Autowired` на поле.
- Входные и выходные DTO отделены от JPA-сущности, есть маппер `toResponse`.
- Bean Validation на создание записи плюс глобальный обработчик, который отдаёт ошибки по полям: `{"errors": {"title": "..."}}`.
- 404 через `ResponseStatusException` вместо `null`.
- AES-256-GCM реализован грамотно, ключ берётся из окружения.
- Для JPA сделан `protected` конструктор без аргументов.
- Современный стек: Java 21, Spring Boot 3.x, Jakarta EE.
- Небольшие последовательные коммиты: validation → database → CRUD → encryption.
